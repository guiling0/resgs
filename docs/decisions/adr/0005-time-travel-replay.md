# 0005-对局可复现与时光回溯

> 状态：已定案 · 日期：2026-08-03

## 背景

需要支持将游戏进度回溯到过去的某个时间点（如上一个回合开始），由真实玩家接手继续。回溯的关键约束：回溯后随机结果必须与"原进度本应产生的结果"一致，且游戏能从此前状态继续执行。

## 结论

### 1. 随机可复现（地基）

- 房间持有 `randomSeed`，所有随机操作（当前 `shuffle`/`randomInt`）统一经 `room.shuffle`/`room.randomInt` 使用该种子并推进
- 相同初始种子 + 相同输入序列 + 相同随机调用顺序 → 每次随机结果完全一致
- **硬性约束**：禁止直接 `Math.random`、依赖系统时间或网络时序的分支；重放路径不得含环境相关代码

### 2. 回溯形态对比

| 形态 | 说明 | 代价 |
|---|---|---|
| 纯回放 | 新开一局（相同种子）→ 重放历史命令日志到目标点 | 实现简单；每次回溯重放整局 |
| checkpoint + 日志 | 每回合保存状态快照（含 `randomSeed`）+ 命令日志分片；回溯 = 加载快照（O(1)），目标在快照后则重放其后少量日志 | 需完整状态序列化 |
| 纯快照 | 仅加载快照 | 最快；**仅对执行态为空的干净点有效** |

### 3. 执行态不可序列化（关键约束）

事件列表、进行中的结算、等待输入的会话等**运行时执行态无法序列化**（含闭包/回调/调用栈）。

- 回溯点处于**执行态为空的干净点**（回合开始、阶段开始等结算完全结束处）→ 静态状态快照 + `randomSeed` 即可恢复，无需重放
- 回溯点处于**结算中间** → 纯快照无法继续，必须经日志重放**重建执行态**
- 因此："回溯到上一回合开始"这类回合边界回溯可用快照；任意点通用回溯以回放为主

### 4. 序列化不限于 StateNode

状态同步快照（snapshot/patches）依赖 `StateNode`/装饰器，但序列化本身不依赖该基类——非同步实体（如 `Area`）可自行实现 `toJSON`/`fromJSON` 参与快照。
