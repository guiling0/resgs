# 0008-技能"修改描述"（技能增强：五虎将大旗模式）

> 状态：已定案 · 日期：2026-08-08

## 背景

部分技能的规则形式是"修改其他技能的描述"，如君刘备【五虎将大旗】："存活的蜀势力角色技能分别按以下调整：武圣——将'红色牌'改为'任意牌'……"。这类"修改描述"本质是**条件性技能增强**，需要与状态效果框架统一。

旧项目实现（君刘备 五虎将大旗）：

1. **描述层**：大旗技能 `desc` 直接列明各技能调整文本；五虎将自身 `desc` 不变。描述是规则书的文本说明，**不**运行时改描述。
2. **实现层**：大旗生效状态 = 房间级标记 `room.setMark('wuhujiangdaqi', this.check())`，由大旗技能带一个 `level` 状态效果在每回合 `on_refresh('before')` 时机重算；五虎将各技能带一个"增强分支"（独立效果或内联分支），激活条件统一查该标记：
   - 关羽武圣：内联改过滤条件（大旗生效时任意牌，否则红色牌）
   - 黄忠烈弓：独立 `wuhu` 状态效果，`Range_Correct` 回调查标记 → 攻击范围 +1
   - 赵云龙胆：独立 `wuhu` 触发效果，查标记 + 牌是转化牌 → 摸一张
   - 张飞咆哮：独立 `wuhu` 锁定效果，查标记 → 目标加失效效果（无视防具）
   - 马超铁骑：effect 内联分支，查标记 → 全部明置武将牌，否则选一张

### 旧项目模式的问题

1. 标记是魔法字符串，靠人肉保持一致；靠 `on_refresh` 每回合刷新，**刷新时机驱动**，回合中途失效（如被禁）可能滞后。
2. "事实"与"消费方"脱节：大旗列明的调整散落在五个技能文件，无集中对应。
3. 内联分支侵入原效果代码（关羽、马超）。
4. 客户端无法展示"增强后"的描述（描述文本静态）。

## 结论

### 1. 大旗建模为状态效果实例（自包含有效性）

不刷新标记，让大旗本身是一个状态效果实例，自包含有效性判定。新增状态回调类型：

```ts
/** 技能效果被外部增强/修改：命中即该效果受增强 */
[StateEffectType.SkillModify](effect: Effect): boolean
```

- 大旗状态效果定义该回调（判定"effect 所属角色是存活的蜀势力"），其自身 `check()`（失效判定 + condition）即"大旗是否生效"——**实时求值，不需要刷新时机**；
- 五虎将增强分支的激活条件从 `room.getMark('wuhujiangdaqi')` 改为 `room.getStates(SkillModify, [this.effect]).some(Boolean)`；
- 君刘备失去技能 / 大旗被失效 → 状态效果失效（依托失效框架）→ 增强自动解除，状态同步随状态效果挂载走。

### 2. 增强分支保持"每技能独立效果"

五虎将增强形式差异极大（改 filter、加修正、加触发、加失效效果、改目标选择），强行抽象成统一的"修改数据"只会退化成一堆 switch。**增强逻辑留在各技能定义内**，只替换激活条件的查询来源，不动结构。

### 3. 描述层维持静态

`desc` 维持静态文本，大旗 `desc` 列明调整（同旧项目）。"修改描述"的文本仅作规则说明，不实现运行时文本重写。

### 4. 可选（暂不做）：描述修改片段

若未来需要客户端展示"增强后"的描述，可定义"基础描述 + 修改片段"模板（如 `desc: '你可以将一张{0}当【杀】使用或打出。'` + `modify: { wuhu: ['红色牌', '任意牌'] }`），大旗命中时客户端拼接展示。成本高、仅展示层收益，当前不做。
