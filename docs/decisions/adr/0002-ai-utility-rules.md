# ADR-0002：AI 架构 — 效用评分规则 + 演进钩子

**日期**：2026-07-18
**状态**：已决定

## 上下文

旧项目无 AI（`core/ai/` 为空目录，电脑玩家 = 超时 0.1s 取第一个合法选项）。旧 `discuss/ai-design.md` 提出 CBR（案例推理）+ 规则混合方案，存在致命问题：

1. CBR 需要数万局训练数据，个人项目对局量撑不起案例库
2. 延迟归因噪声大：一场游戏的胜负是数十个决策叠加，outcomeScore 无法准确归属到单个决策
3. 与 MongoDB 耦合将 AI 核心逻辑绑定到持久化层，破坏 `shared/` 的纯逻辑边界

## 决策

**采用效用评分规则 AI，为学习型和模拟型演进留门。**

当前阶段（Phase A）：
- AI = `IPlayerInput` 的一个实现，对引擎零改动
- 纯 TypeScript 规则引擎（`shared/ai/`）：共享评分表 + 卡牌价值表 + 5 个 evaluator
- **零配置技能感知**：扫描 `room.triggerEffects` 自动检测场上技能，不手动写标签
- **MVP 评分系统**：与 AI 共享同一套 `sgs.scoreTable`，同时服务战报排名和 AI 调试

演进钩子（Phase A 即埋，不实现）：
1. 决策日志（为后续学习型积累数据）
2. **seeded RNG**（随机源可注种子——模拟型 AI、录像回放、bug 复现的共同前置）

远期方向：
- Phase B（学习型）：离线权重调优 / CBR 轻量版（数据够了再考虑）
- Phase C（模拟/搜索型）：headless 自动对战 + 抽样确定化模拟 / MCTS

## 替代方案

### CBR + 规则混合（旧方案，已弃）

- 优点：理论上可学习，自动适应新技能
- 缺点：数据饥饿、归因噪声、冷启动、MongoDB 耦合
- 为何不选：设计超前于项目实际需求。规则引擎先证明自己，数据积累后再考虑学习型。

### 蒙特卡洛树搜索

- 优点：不需训练数据
- 缺点：事件引擎异步、状态快照成本高、三国杀状态空间大（不完全信息 + 多玩家）
- 为何不选：Phse C 时才可行（需要 seeded RNG + headless 自动对战基础设施）

### 纯规则（不埋钩子）

- 优点：最简
- 缺点：锁定当前方案，后续加学习/模拟型需要打破 API
- 为何不选：埋两个钩子（决策日志 + seeded RNG）成本极低（~几十行），但避免未来改 API 的巨大摩擦

## 影响

- `shared/ai/` 目录新增（纯 TS，客户端可复用）
- AI 作为 IPlayerInput 实现，引擎零修改
- 身份局最小可玩（里程碑 M4）后立即启动 Phase A，自动对战反哺技能调试
- MVP 评分系统同时服务 AI 和战后战报
